# 需求、商业与技术分析

研究日期：2026-10-24。本文区分已核实的工具能力、产品设计决策和待验证商业假设；不以竞品存在推导市场规模或付费意愿。项目暂名 **wawawa**。

## 1. 产品定义与核心判断

目标产品是一套面向中文分支互动音频故事的创作与运行系统：作者写出有因果关系的故事，玩家通过口头选择参与；旁白和虚拟角色拥有各自的声音，可配合音乐、音效。好感度、关键事件与历史选择决定之后的选项和结果。

核心体验应是“听一段故事，作一个决定，听到可信的后果”。固定剧本和明确状态保证长线伏笔可靠；AI 适合辅助创作、配音制作和将自然表达匹配到现有选项。故事状态不能交给模型聊天记忆维护。

当前 MVP 是该产品的**创作与剧情验证工作台**，不是已经可在任意音箱运行的纯语音成品。先证明“故事可创作、分支可执行、状态可保存、结果可解释”，再验证真实声音体验。

## 2. 用户、场景和价值主张

### 首批用户假设

- 玩家：喜欢中文剧情向游戏、广播剧或有声书的成年人，愿意在安静的私人空间用简短语音参与故事。
- 创作者：能够编写短篇剧情，但不希望开发完整游戏客户端的独立作者或小型内容团队。
- 设备合作方：希望为兼容语音终端增加可重复体验内容的开发者。设备合作是后续分发渠道，不应成为首版依赖。

优先试验睡前、居家休息等低干扰场景。公共交通中开口回答的社交成本、驾驶场景的注意力分散，均不适合作为首轮主打卖点。

### 价值假设

| 对象 | 当前替代方式 | 本项目尝试改善什么 | 需要的证据 |
|---|---|---|---|
| 玩家 | 有声书、广播剧 | 从被动听故事变成作出有后果的决定 | 用户是否能感知选择对后文的影响 |
| 剧情游戏玩家 | 阅读式 AVG / 互动小说 | 在无需看画面的情况下体验角色和分支 | 闭眼完成率、选项记忆负担、重听次数 |
| 作者 | Ink 编辑器加自制前端 | 在同一工作台验证发布版本、对话和状态 | 完成一个可玩短篇所需时间、错误定位成功率 |
| 设备方 | 通用闲聊或单向内容播放 | 引入可持续更新、可存档的互动内容 | 接入成本、音频控制能力、跨设备恢复成功率 |

## 3. 需求分层

### MVP 必须完成

1. 在管理界面创建或选择故事，编辑 Ink 源码，保存草稿。
2. 编译源码并显示错误；失败时不产生可玩的发布版本。
3. 发布不可变的故事版本，至少包含编译产物、来源内容和角色元数据。
4. 开始一份独立游玩存档，展示当前台词、说话人和当前有效选项。
5. 模拟器允许点击选项，以及输入“1 / 第一个 / 选项全文”等明确表达；不能匹配时重问，不推进剧情。
6. 对好感度、历史标记、条件选项和结果分支提供可复现的示例与自动化验证。
7. 保存、恢复当前回合；刷新页面后不丢失已经提交的进度。
8. 拒绝过期回合的选择，避免并发或重试重复推进。
9. 作者可验证角色和音色元数据，但界面明确说明尚未实际调用角色 TTS。

### 声音版后续需求

- 按角色绑定音色；同一角色跨段落音色稳定。
- 台词、音乐、音效和停顿可编排；固定台词优先缓存或预生成。
- 播放结束后进入监听，支持重听、暂停、继续与未识别输入。
- 用户话语只映射到当前选项；无有效匹配时不替用户作决定。
- 手机与兼容设备共享账户、版本和存档。

### 当前明确不做

开放式角色聊天、实时生成整条剧情、3D/2D 游戏引擎、动画、图片、多人协作编辑、付费系统、内容市场、任意音箱兼容、真实声纹登录。MVP 不承诺真实 ASR/TTS、小智实机或手机锁屏体验。浏览器若有系统朗读实验能力，也不作为跨平台语音验收依据。

## 4. 同类工具与选择

| 工具 | 可核实能力与定位 | 对本项目的适配判断 |
|---|---|---|
| Ink / Inky / inkjs | Ink 支持分支叙事；Inky 编辑预览；inkjs 可在浏览器和 Node.js 执行；运行时支持状态保存恢复 | 首选。轻量服务端执行与确定性状态符合核心需求；音频演出需自建 |
| Yarn Spinner | 对话脚本、说话人、游戏引擎集成；有台词关联配音和本地化资源的流程 | 多角色对白工具强，但当前不使用游戏引擎，优势不能全部直接复用 |
| Twine | 可视化编辑非线性故事，导出 HTML；简单故事无需编程 | 作者入门容易，但仍需重新适配集中式存档、音频和语音输入 |
| Ren’Py | 视觉小说引擎，角色、声音与图像演出生态完整 | 未来有视觉客户端时值得考虑，当前会引入大量不需要的运行界面 |
| articy:draft | 角色、对白、任务及叙事资料的可视化管理 | 适合更大内容团队，首版规模不需要完整叙事生产平台 |

不能仅用 GitHub stars 或知名游戏个例宣称某工具拥有最多用户。本项目选 Ink 的依据是运行方式与状态模型，而非未证实的市场排名。

## 5. 技术方案

### 基础栈

- 后端：Node.js、TypeScript、Fastify、inkjs、MongoDB。
- 前端：Vite、React、TypeScript。
- 部署初期：一个 API 服务、一个前端构建产物、一个 MongoDB；无需消息队列或微服务。
- 后续音频：对象存储保存媒体，数据库保存资源索引和角色配置；大音频不作为一般存档字段写入 MongoDB。

### 职责边界

剧情核心接收合法选择，产出台词、标签、当前选项和新存档；它不依赖 HTTP、MCP、React 或某个 TTS 厂商。HTTP 与未来 MCP 是调用同一应用服务的适配层。模拟器是验证工具，不应在浏览器自行重新计算并覆盖服务端剧情状态。

### 发布与存档

草稿可以修改；已发布版本不可变。新会话绑定具体发布版本，旧会话继续使用原版本，避免故事修改导致历史存档失效。需要同时保存完整 Ink 状态和当前回合的展示内容：推进至选择点后的状态不能自动重建此前已经读出的台词。

MongoDB 单文档写入具备原子性。将会话版本号、Ink 状态和当前回合放在同一文档，更新时带上期望版本号，可以避免两次请求同时推进。对重试应识别同一请求并返回既有结果，或明确拒绝过期回合；绝不能悄悄执行第二次。多文档业务以后再评估事务需求。

运行时需要为单次推进设上限，防止作者写出的循环使 API 长时间占用。限制源码、标签和返回内容大小；编译错误和运行错误不能覆盖上一次有效存档。

### 角色与声音元数据

使用稳定的角色 ID，并将显示名、音色标识和默认演出参数独立配置。台词标签负责指出说话人、情绪和资源 ID。音色标识只是配置，不代表配音已经生成或声音质量已验证。MVP解析并展示标签；真实音频阶段再加入未知角色引用检查和明确的旁白回退规则，不承诺初版进行所有条件路径的静态分析。

## 6. 小智与 MCP：已知事实和待验证事项

小智提供外部 MCP 桥接示例；固件通信协议包含音频上传、下行音频、语音识别结果及 TTS 生命周期消息。MCP 工具结果能携带文本和音频，但宿主是否原样朗读、自动播放或转交用户每一句原话，由具体实现决定。

官方角色配置支持更换音色，不足以证明同一回复中能通过外部 MCP 动态切换多个角色声音。通用固件工具也不能等同于所有设备均具备任意 URL 播放能力。因此，“接入点上线”不能作为“多角色音频游戏已经接通”的验收标准。

下一阶段必须用目标设备验证：返回预混多角色音频 → 原样播放 → 播完进入监听 → 回答通过工具提交 → 正确推进一轮。若托管云无法提供可靠闭环，则评估自建兼容后端；这与继续使用 xiaozhi.me 托管云是不同路线，应记录成本和能力差异。

## 7. 商业模式假设与验证

首轮只验证一个内容方向，例如 10～15 分钟的悬疑互动短篇；避免同时做恋爱、教育、儿童故事和工具平台。时间、目标和人数均是试验设计，不是市场事实。

可评估的收入模式：单故事付费、内容包、创作者按音频生成量付费、设备内容授权。早期不叠加所有模式。首先确认用户是否愿意完成一次并重玩，随后再测支付意愿。

建议以 5～8 名目标玩家、2～3 名创作者进行可观察试用，记录：

- 从开始到首个有效选择的成功率；完整短篇完成率。
- 听完选项后是否需要看屏幕、重复或解释。
- 用户能否指出某个早期选择产生了后果。
- 是否主动重玩另一条路线、愿意推荐或付费，以及具体原因。
- 作者能否独立修改台词、发布并复现一个分支。

小样本只用于发现体验问题，不用于推断总体付费率。保留访谈原话和反例；用户说“有趣”不能替代实际使用或支付证据。

单位成本模型应包含：语音识别分钟数 × 单价、动态 TTS 字符数 × 单价、音频存储与流量、可选模型调用、内容制作/审核成本。预生成和缓存能降低重复配音成本，但可能增加初次制作工作量。暂无真实服务报价和用量数据，不给出毛利率或市场规模结论。

## 8. AI 价值与工程证据

MVP 的产品价值先来自可靠的互动叙事工作流。**使用 AI 开发并不等于产品已拥有 AI 功能。** MVP 不应以角色配置标签冒充多角色 AI 配音。

优先补充的可展示 AI 能力是“作者选角色音色，生成并预览台词配音”；其次是“将自然表达约束映射到已有选项”。AI 辅助分支检查可作为后续作者功能，必须展示输入、建议和作者采纳结果。

AI 工程效率的证据应是可审计的规格、任务划分、PR、测试与缺陷修复记录，而非仅声称生成了多少代码。每轮以验收用例和实际输出检验代理成果；记录模型提出但被测试否决的方案，也能体现工程控制。

## 9. 主要风险及应对

| 风险 | 后果 | 当前行动 |
|---|---|---|
| 只有编辑器，缺少玩家体验 | 产品价值和 AI 呈现不足 | 提供完整可复玩样例；下一优先项是短篇真实音频闭环 |
| 分支数量膨胀 | 写作、配音和测试成本快速增加 | 采用分支后汇合、变量驱动的有限变化；先做短篇 |
| 多个音箱能力不一致 | 集成成本失控 | 先支持一个明确设备，契约测试通过再扩展 |
| 模型重述台词或猜测选择 | 剧情失真、误选 | 播放原始音频，服务端校验当前有效选项 |
| 纯语音记忆负担 | 玩家忘记选项或上下文 | 每轮优先 2～3 项、短名称、允许重听 |
| 版本更新破坏存档 | 用户丢失进度 | 不可变发布版本，存档固定版本 |
| 作者内容不可信 | 运行耗时、资源滥用 | 源码与运行预算限制，编译失败不发布 |
| 配音授权与成本 | 无法合法发布或难以盈利 | 使用有明确许可的音色和音乐，按真实用量核算 |
