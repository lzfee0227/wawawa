# 开发路线与交付计划

## 目标与取舍

最终目标是一个可在手机和兼容语音设备上运行的中文互动音频故事系统：作者发布有角色声音、音乐和长期因果关系的内容，玩家通过选项参与，并跨设备继续进度。

比赛窗口为 1～2 天。阶段 0 和阶段 1 已经交付可验证的剧情创作闭环。下一项是标准 MCP 游玩适配。真实语音与小智接入必须独立验收，不能用 MCP 工具返回的文字代替实机证据。时间预算是规划估计，遇到外部阻塞时优先保住核心闭环和测试。

## 阶段 0：规格与基础（已完成）

- 明确需求、数据模型、API、错误行为和验收场景。
- 建立 AI 协作规范、PR 模板、持续集成及本地验证说明。
- 建立带历史标记、好感度和条件分支的中文样例。
- 在编码前记录初始评审与最严重的产品风险。

出口：团队对“草稿、发布版本、会话、回合”的含义一致；每项核心需求有可执行或可手动复现的验收步骤。

## 阶段 1：核心引擎 MVP（已完成）

交付后端剧情编译、发布和会话运行，以及可直接操作的管理界面和模拟器。

### PR 建议划分

| PR | 内容 | 主要验收 |
|---|---|---|
| 规格与工程基础 | 文档、工作区、工具链、CI | 文档可导航，类型检查和测试命令明确 |
| 剧情核心 | Ink 编译、台词标签、条件选项、存档 | 样例分支单测、编译错误、运行限制 |
| API 与持久化 | MongoDB、故事版本、会话、回合提交 | 真实 MongoDB 集成测试、恢复、竞争提交 |
| 创作与模拟界面 | 源码编辑、错误提示、发布、模拟对话 | UI 测试和从编辑到结局的 E2E |
| 演示验收与改进 | 样例完善、可用性修正、评审证据 | 全部质量门槛通过，演示可复现 |

后端和界面可在契约确定后并行开发。每个 PR 保持一个可说明的目的；依赖 PR 合并后再重放依赖分支。不得通过直接推送主干绕过 PR；空仓库基点初始化属于单独的仓库管理问题，不包含功能文件。

### MVP 必须演示的完整故事

1. 作者修改一行台词并保存。
2. 故意制造编译错误，看到错误且不能发布。
3. 修复后发布，创建游玩会话。
4. 第一轮选择改变历史标记；随后选择改变好感度。
5. 后续出现不同选项，或同一选项产生不同结果。
6. 刷新并恢复，回合内容一致。
7. 重开另一份存档走另一条路线，不影响原存档。
8. 发布新版后，旧存档继续固定在旧版。

出口：核心逻辑、API 集成、UI 和 E2E 都有证据；不能只有截图，也不能以“页面能打开”代替游戏验证。该出口已由本地运行和远端 CI 达到。见 [MVP 运行验收](reviews/mvp-validation.md)。

## 阶段 2：标准 MCP 游玩适配

让标准 MCP 客户端游玩已发布故事。模型只能朗读服务端回合并提交当前选项，不能改草稿、编译或发布。行为见 [SDD-002](specs/002-mcp-play.md)。

### PR 划分

1. 规格：工具、快照、错误和两种入口的验收要求。
2. 游玩工具与进程内客户端测试。此时还没有可被外部拉起的进程。
3. stdio 入口、API 进程上的 `/mcp`、启动说明。HTTP 若无法与现有进程干净共存，只合并 stdio，HTTP 另开一个 PR。

出口：M01–M08 有运行证据。文档仍写明没有配音、没有语音识别、没有小智实机。该出口已由进程内客户端、HTTP `/mcp` 和失败启动的 stdio 达到。见 [MCP 游玩评审](reviews/mcp-play.md)。

## 阶段 2.1：工作室里的 MCP 测试台

让作者留在管理界面里，当作标准 MCP 客户端调用已发布故事的游玩工具，并看到真实返回的台词、选项、错误和 `play_turn` 约束。行为见 [SDD-003](specs/003-mcp-console.md)。

### PR 划分

1. 规格：客户端信封、界面和 C01–C07。
2. 浏览器 MCP 客户端与单测。此时还没有可见页面。
3. 测试台标签、组件测试、真实 `/mcp` 的浏览器流程和阶段记录。

出口：C01–C07 有运行证据，见 [MCP 测试台评审](reviews/mcp-console.md)。测试台是人工操作的协议客户端。它不提高“宿主模型已经照读”或“故事已经出声”的结论。

## 阶段 3：短篇可听闭环

此阶段按收益排序，不扩成通用平台。

1. 若游玩适配稳定且时间允许，接一个明确的 TTS 服务或导入合法配音，为两个角色加旁白制作短篇音频；明确展示缓存和生成耗时。
2. 音频播放完成后接收选择；再逐步加入真实麦克风。没有实测时不要标记“纯语音完成”。
3. 补一份短篇试用记录，验证玩家是否听懂历史选择的后果。
4. 更新阶段评审，展示已解决问题和仍然存在的能力边界。

出口：一次连续演示能解释产品价值、架构取舍、AI 实际贡献和工程质量。若未接真实音频，明确称为创作、引擎与 MCP 游玩适配，不称为语音游戏。

## 阶段 4：手机声音闭环

- 完成角色音色、台词音频生成/缓存、音乐与音效编排。
- 实现播放、完成、失败、暂停与重播的明确状态。
- 语音识别只匹配当前选项；不明确时重问。
- 实测目标手机浏览器或 App 的麦克风权限、后台和锁屏行为。
- 从短篇完成率、识别纠正次数、时延、重玩意愿评估体验。

出口：至少一款明确手机环境能不看屏幕完成短篇；保留环境版本、结果和失败案例。浏览器支持不足时评估原生壳，不能仅增加提示词。

## 阶段 5：单设备试点与跨设备存档

- 在已经运行的标准 MCP 服务上检查目标设备，验证音频播放后继续监听。
- 检查 xiaozhi.me 实际工具返回和目标设备能力。接入点在线不算语音游戏已经接通。
- 明确设备身份如何绑定玩家；避免把智能体或设备 ID 直接等同于自然人。
- 若托管云不满足演出控制，记录实测结果并决定是否自建兼容语音后端。
- 手机与一款小智设备交替恢复同一会话，测试断网和过期请求。

出口：公开支持矩阵中只有实测成功的设备；不承诺所有音箱。每个新设备复用协议测试和实机验收清单。

## 阶段 6：内容与商业验证

- 以一个细分题材试运营，邀请少量作者完成短篇。
- 引入基本账号、访问控制、音色/音乐授权记录和成本预算。
- 试验单故事或内容包支付意愿；在真实数据基础上确定定价。
- 增加台词 ID、配音重生成、内容审核和版本发布管理。
- 优先解决作者制作成本与玩家留存，不先建设大型交易市场。

出口：获得可复现的使用、内容成本与支付证据，并能解释与有声书、文字游戏及通用角色聊天的差异。

## 阶段 7：长期产品形态

形成可复用的叙事运行服务、作者声音工作台及设备适配层。支持更多故事和语言、受控的创作协作、分支覆盖分析及有依据的内容推荐。

最终验收关注：故事状态可靠、角色声音一致、无屏幕可用、跨设备可恢复、内容供给可持续、成本可测量。实时自由剧情、多模态动画和通用游戏引擎不是必然目标，只有用户证据支持时才加入。

## 每阶段回顾机制

每个可演示阶段结束更新 `docs/reviews/`：按产品与商业 50%、架构 20%、产品 AI 15%、AI 工程效率 15%分别评分；列出证据、最大三个缺口、下一次最小改进。分数不得因计划存在就上调，只能依据已经可观察的结果变化。

若评分未达到展示目标，优先修复最影响体验或可信度的问题；不靠增加页面和功能数量提升自评。安全边界、尚未运行的测试、未接通的外部服务都应如实记录。
